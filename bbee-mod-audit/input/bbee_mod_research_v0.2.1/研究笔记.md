## 0. 结论与验证范围

这个上传包不是只有一个角色成品，也不是只有启动器。它包含 Terminal 界面、实际工作的 Python 补丁构建器、共享 JavaScript 接入模块，以及 Nine、Ruby Rose、DELTARUNE: Party 三个角色项目。Ruby 还保留了从动作定义生成角色描述符、动作树和资源的脚本，因此可以从源码学习，不再依赖找回 Discord 原帖。

**已经追清的内容**：角色包如何被识别；为什么 Ruby 初次没有 mod.json；数据、JS、资源如何组合；如何生成帧动画与攻击逻辑；如何打包进游戏；安装与卸载为什么涉及存档；一个实际攻击怎样从输入表连到动作、判定、动画和伤害记录。

**已经实际做出的内容**：一个依赖 dr-party 的单字段配置补丁，以及四项通过的离线表组合测试。

**没有完成的内容**：未启动上传的 EXE/BAT、完整安装器或游戏；未针对用户当前游戏运行完整构建；未生成或实测完整新角色；未验证联机兼容；未对二进制或所有第三方依赖进行安全审计。

不要把“代码能够解释”“语法检查通过”“离线组合正确”“游戏实际可用”当成同一个结论。本笔记将其分开记录。

## 2. 这条制作路线究竟是什么

```text
玩家本地、对应版本的原版游戏文件
  → pipeline.py：读取 manifest 与 merge.json，切出逻辑资源包
  → 提取 TextAsset，恢复 JS 与表格数据、准备结构信息
  → Terminal 按需执行角色的 prepare
  → mod.json：描述表格、脚本、资源与依赖修改
  → bbmod.py：按依赖顺序组合
  → 克隆基础资源 / 运行导入器 / 写入动作树
  → 编码表格与 JS，构建 AssetBundle
  → make_patch.py：写 m_mod.m，更新 merge.json 与相关依赖
  → 游戏自己的 JS、角色系统和资源加载机制使用这些内容
```

**这是对该包的准确描述，不是 BepInEx 插件教程。**这里的角色实现并不是把一个新的 C# DLL 放进 BepInEx/plugins。不能把其他《苍翼》Mod 的 BepInEx/Il2CppInterop 方案当成这个包的必选前置。并不因此否定游戏还存在其他 Mod 路线。（E04、E06、E08、E09）

源码确实调用游戏已有的 JS/C# 桥接对象，例如 `csharp_1`、`Util_1.U`。只凭这些调用不足以确定具体桥接框架品牌，不把它擅自叫成 PuerTS。

### 2.1 资源为什么不是随便覆盖一个文件

`merge.json` 记录逻辑资源 `r`、实际物理文件 `m`、偏移 `s`。构建器根据同一物理文件内的下一条偏移计算每个逻辑包的边界。修改后把相关资源集合写入 `m_mod.m`，并把索引指向新位置。（E04、E09）

所以只复制某个贴图文件、只改资源名字，甚至只生成 AssetBundle，都不代表游戏能够正确找到它。对象引用、逻辑包索引、依赖清单必须一致。

### 2.2 表名含 xlsx，不代表可以直接用 Excel 编辑

逻辑目录有 `data/xlsx/...`，但本实现读取的是序列化二进制配置，经 schema 解码后变成 JSON，再编码回去。`bbmod.build()` 还处理存在的 FixedPoint 对应表。（E08；`pipeline.py` 中 schema 获取部分）

Protocol Buffers 的二进制记录使用字段编号，字段名和精确类型需要 schema 解释；“有二进制就能凭字段名改表”不成立。[外部前置 P1]

## 3. 加载与构建生命周期

### 3.1 terminal.json 和 mod.json 不是同一种东西

`terminal.json` 供 Terminal 界面发现角色、描述依赖和安排预生成任务。Ruby 的 prepare 包含：

```text
mods/char-ruby/build_ruby.py
mods/char-ruby/terminal_art.py
```

`mod.json` 才是 `bbmod.py` 消费的补丁描述符。GUI 先在需要时 setup，再 prepare，最后 install。因此脱离 GUI 直接运行底层安装命令，并不能假定它会自动完成 Ruby 的预生成。（E02、E03）

### 3.2 依赖与覆盖

`resolve_order()` 做依赖拓扑排序；缺依赖、循环依赖会报错。覆盖另一个 Mod 已修改的普通字段时，声明依赖可以表达“我是在它之上继续修改”，而不是两个独立 Mod 无意争用同一字段。（E05；`bbmod.py:96–106`）

这不是全面的冲突隔离机制。普通字段写入有冲突报告，但 `$append`、整体替换、克隆与资源修改并不等同于完整覆盖检测。不能说“加载器没报冲突，所有资源就肯定互不影响”。

### 3.3 构建先后关系

`bbmod.build()` 的实际核心顺序如下：（E08）

1. 读取启用列表、解析依赖，清理本次输出目录。
2. 组合 tables、JS、locale。
3. 执行 rigClones / bundleClones。
4. 执行 content.importers；导入器接收 `--out` 和 `--adds`，返回 names、entries、guids 等依赖补充。
5. 写动作树和其他 asset 操作。
6. 收集错误；出现 ERROR/CONFLICT 则中止成功构建。
7. 编码配置表与必要的固定点表，做编码往返校验；重建 JS 与本地化包，写 `_build.json`。

给一个原本不存在的资源包写入动作树之前，必须先准备它；引用新网格/贴图之前，也必须把依赖加入清单。这些不是可以随意交换的步骤。

## 4. 一次真实攻击如何成立：Kris 第一段地面普攻

选择 Party 而不是尚未生成的 Ruby，是因为它随包提供可直接检查的动作树。精确对象路径与原始固定点值见 `kris_attack_trace.json` 以及 E18。

```text
Attack 输入
  → SkillActivate 中 ActorId=200801 / Group=1 / Order=1
  → Action = kris_a1
  → kris_tree.json 的 _actions 中同名状态
  → Animate = kris_atk1
  → HitDataList 的时间窗、碰撞盒、命中反馈
  → SkillDamage 中同角色、同动作的伤害记录
  → 特效与动作切换
```

| 层 | 在包中读到的值 | 正确理解 |
|---|---|---|
| 入口 | Input=Attack，AllowGround=true | 输入条件，不是动画本身 |
| 预输入 | Preinputtime=0.20 | 预缓冲配置；不是攻速倍率 |
| 逻辑名 | kris_a1 | 动作状态的连接点 |
| 动画名 | kris_atk1 | 被动作状态引用的画面序列 |
| 配置时长 | TotalDuration 约 0.35 | 由固定点值换算，非录像实测 |
| 首个命中窗 | Start 约 0.05，End 约 0.1667 | 动作内部的命中时间配置，非整段全程有判定 |
| 伤害配置 | DamageRatio=[1.1] | 该表中的比例参数，不等于最终显示伤害 |
| 特效引用 | Role/Kris/kris_slash_1 | 还需要特效资源与引用正确 |

这里把时长按脚本的秒制约定理解；实际输入响应、命中、顿帧和受击结果仍受运行时逻辑影响。**这些都是静态配置结论，不是已在游戏验证的手感。**（E13、E18）

由此可明确分工：换画面应追动画/网格/图集；改可取消时间应追输入门槛与 ActionSwitchs；改判定应追 HitDataList；改伤害要追伤害记录及后续运行时计算。把它们全当成“改动画”会造成画面与规则不同步。

## 5. Ruby 的完整制作样例能学到什么

### 5.1 基础角色借用，不是整套从零重造

`build_ruby.py` 明确声明：Ruby ActorId=200701，基础角色 DONOR=100101，基础逻辑 `rg`，新角色逻辑 `rrb`，子弹体逻辑 `rrbb1`。脚本复用并转换基础角色的移动、落地、受击、死亡等玩家状态，同时接入自定义攻击、弹体、潜能与特效。（E11、E12）

因此新增完整角色的实用方法是：复用一个适合的可玩角色基础设施，替换资源与攻击，再清理基础角色特有的条件和路线。直接复制敌人或其他角色的整棵动作树，可能残留不存在的潜能、状态、脚本或动作引用。`fix_player_state` / `assemble` 就在处理这类问题。（E15；`own/bossport.py:302–344`）

### 5.2 画面：图集、网格、定制帧数据

`own/tools/bbtag/bbtag_rig.py` 的实现不是“生成普通 Animator Controller”。它整理每段动画的 sprite/ticks 序列，创建图集与对应网格，克隆并填充游戏使用的 MonoBehaviour 动画数据。（E16）

实际字段包括：

```text
Frames: 每帧 mesh 的 m_FileID/m_PathID、textureIdx、mountPoints
Indeces: 累计帧边界（源码确实拼作 Indeces）
TotalFrameCount: 累计 tick 数
Context.AnimationRoleName: 新角色资源名
```

该导入链以源动画帧/tick 构建序列；不能由此断言所有游戏子系统都固定运行在同一个帧率。构建资源还处理纹理页、透明度相关处理、外部 CAB 引用、预加载表和依赖映射。只导出 PNG 会遗漏大部分工作。

### 5.3 攻击、判定与特色机制

`build_logic()` 生成 `rrb_tree.json`、`rrbb1_tree.json` 及特效计划；`input_rows()`、`damage_rows()` 生成输入与伤害配置。`write_mod()` 把克隆的角色表、潜能、本地化、资源生成器、动作树和 JS 接入写成同一份描述符。（E12；具体函数位置见 `static_audit.json` 的 python_index）

Ruby 还将 `src/rrb_runtime.js` 追加到游戏的 BuffFuncs 模块，将 `src/rrb_hud.js` 追加到 BattleUI。这样实现的不只是外观，也包括自定义命中效果、状态处理和界面反馈。应按调用链判断效果如何触发，不把脚本函数名当成已经验证的玩法描述。

### 5.4 生成“完整新角色”的必要闭环

角色身份与选择入口；基础动作与受击死亡状态；动作资源；输入与取消条件；判定与伤害；潜能/成长/传承入口；HUD/本地化；资源依赖；存档引用；打包和卸载。

一个只有站立与攻击画面的角色仍然不完整。最先要做成的纵向切片，是“选择进入 → 移动/受击 → 单次攻击命中 → 战斗结束 → 退出重开”闭环，而不是先制作几十段动画。

## 6. 必须真正理解的三套引用与一种数值格式

### 6.1 PPtr：Unity 对象引用

`m_FileID` 与 `m_PathID` 指向对象，可能落在当前或外部资源文件。角色网格、动画、材料等连接依赖它；重命名资源不等于改好了引用。（E16）

### 6.2 managed reference：动作条件引用

动作条件常通过 `rid` 指向 `references.RefIds` 里的记录，记录包含 class、namespace、assembly 与数据。Unity 的 SerializeReference 机制给宿主内的对象分配引用 ID，并在序列化数据中保留类型与字段信息；它不是全游戏通用的任意编号。[外部前置 P2]

包内的 `Refs` 工具生成这些记录，`assemble()` 收集所需引用，并检查缺失引用。不能只把一个新 class 字符串写进 JSON，就期望游戏拥有这个新条件类。（E14、E15）

上传包使用非常大的整数 RID。普通 JavaScript Number 的最大安全整数为 2^53−1；对这类 JSON 做不加处理的 JSON.parse / JSON.stringify 可能损失整数精度。Python 的整数读取不需要先转成浮点数。编辑时应保留原整数，必要时使用能保存大整数的解析方式。[外部前置 P3]

### 6.3 manifest / CAB / GUID：包依赖关系

这套关系负责资源包在哪里、依赖什么、文件名如何对应。它和动作条件 rid、PPtr 不是同一个 ID 空间。重建一个包需要同时检查这三层，不应拿一个简单“全局换 ID”函数处理所有字段。（E08、E16）

### 6.4 固定点数值：只转换已确认类型

源码 `bossport.py:35–37` 定义 `FP=4294967296.0`，构造时 round(x*FP)，读取时除以 FP。因此特定包装字段中的大整数经常是固定点时长、位置或速度，不是离谱的大秒数。（E13）

例如 1503238554 / 4294967296 ≈ 0.35。但不应把每个整数、每个 value 字段、或者原本是普通浮点数的字段都按此转换。本包也含普通 float。研究附件只对已确认的动作时间和判定盒包装字段提供 raw/decoded 双值。

## 7. 已做出的最小补丁和实际测试

### 7.1 功能

文件夹 `study-kris-input-buffer/` 仅包含 `mod.json` 和说明。依赖 dr-party，把 Kris 第一段地面普攻输入记录的 Preinputtime 从 0.20 改为 0.30。它不添加完整新角色，也不改动画、判定、伤害。

```json

  "name": "Study - Kris input buffer (offline-validated example)",
  "version": "0.1.0",
  "gameBuilds": ["25627491"],
  "dependencies": ["dr-party"],

      "SkillActivate": [
        {"ActorId": 200801, "Group": 1, "Order": 1, "Preinputtime": 0.30}

```

`gameBuilds` 是这个示例的目标基线，不是已经在该版本游戏中实测的证明。示例README写明受控安装/验证方式；这次没有在游戏执行。

### 7.2 四项组合测试全部通过

采用原包中人工审阅的五个表组合函数以及字面量 KEY_OVERRIDES，在临时目录执行。输入是一条合成原版角色记录，加 Party 发布包中真实的 SkillActivate 补丁。没有 import 整个 bbmod，也没有启动 setup、prepare、install 或游戏。（E19）

| 测试 | 结果 |
|---|---|
| 相对只启用 Party 的结果，只修改指定字段 | 通过：唯一差异为 (200801,1,1).Preinputtime 0.20→0.30 |
| 无关的合成原版记录不变 | 通过 |
| 从同一 .orig 重复组合结果一致 | 通过 |
| 第二个未声明依赖的补丁写同一字段 | 通过：产生预期 CONFLICT 报告 |

这证明我们能按这份组合器的规则构造一个受控配置补丁，不能证明真实原版表、版本锚点、导入器、GUI、资源安装、手感已经全部通过。

### 7.3 特别发现：SkillDamage 的匹配键有歧义

这份 bbmod 的表键：

```text
SkillActivate → ActorId, Group, Order
SkillDamage   → ActorId, HitTimes
```

第二个**不包含 Action**。Party 已提供的前两条伤害记录分别属于 dropend4 与 dropend_show，但 ActorId、HitTimes 相同。直接写“ActorId + HitTimes + Action + 新倍率”的普通覆盖项，Action 不是查找条件，反而可能被当成待覆盖字段。（E05、E19）

此外 `$append` 添加的记录并不像 `$new` 一样更新普通键索引。因此不要照搬单键表的修改方法。应先确定目标行、追加/生成语义与索引行为，必要时修改角色生成代码或使用经过明确审阅的组合器扩展。本次故意选用 SkillActivate 做教学示例，避免提供一个看似简单却可能改错动作的伤害补丁。

## 8. 静态检查结果：有用，但不是安全证明

| JSON 解码 | 38 | 全部成功 |
| 独立 JS 文件与可完整解析的 append 片段 | 21 | Node --check 通过 |
| 已提供的动作树 | 6 | 未发现重复动作名、重复 RID 或未解析 RID |

| 声明的共享/角色依赖 | 见报告 | 均能在包中找到 |

动作树状态数：Nine 主体 237、三个子实体 3/341/21；Kris 主体 102、弹体 84。**这是 _actions 状态记录数，不是独立招式数量。**其中包括工具状态、变体和运行控制状态。Ruby 的树在 prepare 后才生成，不在六棵树统计内。

`node --check` 只检查语法，不执行脚本；它也不验证游戏内的模块、字段、类型、调用顺序或行为是否正确。[外部前置 P4] 替换片段不一定是完整模块，其锚点是否仍存在要拿实际游戏 JS 检查。

附带 `audit_zenith.py` 为原创只读审阅工具，不导入原包模块。需要 Python 3.11+，Node 可选；Node 子进程清除 NODE_* 环境变量，避免环境注入预加载。推荐对原 ZIP 运行：

```console
python audit_zenith.py "ZenithTerminal-0.3.0-alpha (1).zip" --out static_audit.json
```

无 Node 时使用 `--no-node`，结果会注明跳过。这个工具不是恶意软件扫描器，不保证包可信，ZIP 路径与语法正常也不等于可以无条件运行未知安装器。

## 9. 制作和维护时最容易踩的坑

### 当前游戏基线不能凭列表猜

包内提供了 `tools/schema/25627491/proto_schema_snapshot.json`。不同角色声明的 gameBuilds 不完全相同。`bbmod.build()` 对声明不匹配会给 WARNING，不是那里必然硬阻止；其他 setup/存档/备份检查另有约束。必须检查实际游戏 build、原始表结构和 JS 替换锚点。（E08；`pipeline.py`）

TypeTree helper 中的 Unity 版本字符串不等于已经检测到用户实际 Unity 版本。使用源码定义的 API 与包内依赖版本研究，不把网上新版 UnityPy 示例随意拼到这份脚本。

### JS 修改要同时检查锚点和执行上下文

compose_js 用精确字符串替换；缺锚点报错，多次匹配会警告并替换。追加代码依赖其所在原模块的变量与导出。`node --check` 成功不能证明 `Util_1`、`exports` 或游戏对象在该位置存在。（E06）

### Ruby 嵌套源码变化可能不触发自动 prepare

本版 `_needs_prepare` 主要看 mod 顶层 .py/.json 与游戏 build 标记的时间。它没有递归遍历 src/、own/ 或素材目录。修改 Ruby 嵌套脚本/素材后，不能只期待“按钮自动发现变化”，应在开发流程明确重新执行相应生成步骤，再安装。（E03）

### 删除文件夹不等于安全卸载

entry_point 安装前备份存档，并清理被关闭或不再存在的自定义角色。安全卸载先备份、清理角色引用，再还原资源。源码明确说明会移除这些 Mod 角色的传承体和记录；不是无损保留角色进度的开关。（E10）

所以测试前需要独立备份。关闭 Party 来撤销一个仅依赖它的小补丁，可能触发不必要的角色清理；正确目标是只关闭小补丁并保留 Party，然后正常应用。该回退路径也需要实际游戏确认。

### 安装目录、外部资源和程序权限

部分 JS 组合会把 @ROOT@ 展开为绝对目录，原包文档也提醒安装后移动目录会影响外部音频等路径。修改/搬迁后应重新走构建与安装流程，而不是手工替换路径。（E06；包内 READ_ME_FIRST.txt）

content.importers 和 prepare 会执行 Python 程序，它们并非“纯配置”，也不在游戏专用安全沙箱内。此次没有对这些脚本所有路径进行安全认证，不应关闭系统防护来强行运行来源不明的文件。

### 资源使用权与再分发

本研究包只提供原创笔记、验证结果、审阅工具和最小配置补丁，不重新打包原上传包中的字体、商业游戏素材或二进制。学习和技术可行性不代表自动取得美术、音效或其他游戏资源的再分发许可。

## 10. 下一阶段的实施顺序与验收

第一阶段已经完成：读懂发布结构、动作链和组合器，并做出一个可离线验证的配置补丁。

第二阶段是对真实游戏基线验证这个补丁：确认 build、重新读取未混入旧补丁的原始数据；检查目标行唯一性；构建；比较输出差异；用测试存档检查输入、动作、判定、切换和重开。

第三阶段是在已确认可用的角色上改一个动作：保留角色身份、基础移动与存档接入，只改变一个明确的动作或效果；验证动画、时间、碰撞盒、受击、取消与特效一致。

第四阶段才是新角色纵向切片：选择基础角色与独立 ID/资源名；先接入移动、受击、死亡、一个攻击；再扩展技能/成长/界面/完整动画，并测试卸载。对于完全原创美术，还需要按实际自定义帧资源结构设计导入器，不应假装现成 BBTAG 导入器能直接吃任何格式。

进入第二阶段最有价值的证据是用户本地生成的 `inspect/game_build.txt`、Ruby 的生成后 `mod.json`/`gen`、相关配置表、相关 JS 模块与安装日志；如果开发 Inspector 在测试环境可用，再补 F9 报告。**不需要 Steam 账号、不需要整个商业游戏包，也不需要上传完整个人存档。**
